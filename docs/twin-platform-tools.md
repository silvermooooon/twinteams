# Twin platform actions

A Twin acts with its own owner's current platform permissions. It can discover all owner-member chats and people, inspect bounded chat/request/Twin status, open a direct chat or group, rename a group, add members with an explicit history policy, manage its owner's reminders, use Tracking in an authorized chat, and read authorized workspace text. `history` accepts an optional authorized `chat_id`. Tracking in the owner's private chat aggregates its own and authorized group topics, retaining origin chat IDs; group Tracking stays in the originating group even with an explicit tool `chat_id`. Topic details and changes use the origin `chat_id`; `save_summary` stays in the originating chat. Status projections exclude raw request input, frozen prompts, Soul, secrets and execution configuration. Workspace reads require UTF-8 text of at most 64 KiB.

Platform tools reuse the same transaction helpers as human APIs. The SDK operation ID records one `ProductOperation` receipt with an arguments hash. Known origin, destination and source Chat rows are locked in sorted order before rechecking authorization. A reused direct chat preserves its existing history grants/settings. Newly created memberships notify those owners through the existing `personal_changed` / `chats` event so an open client discovers the chat.

`list_authorized_chats` identifies `owner_private_chat_id` and each `is_owner_private`. A group task can send a newly composed owner-attributed report to that private chat or another existing owner-member chat, preserving its original causal chain. No private self-task is created by sending a report. Cross-chat text is a new outward statement and grants no originating-record access to recipients; internal request/manifest/operation audit remains. Explicit cited message IDs are checked against their actual chat and the owner's current history grant, then recorded with `chat_context` envelopes. Reading private history or files adds that boundary to the manifest. Consequently ordinary same-chat group output after such a read remains hidden from members without access to those sources. The Twin should report privately when its context is private. Source withdrawal, membership revocation, private reset and origin cancellation are rechecked before later actions.

Approvals freeze one installed platform write tool or non-replay-safe owner execution tool (bash, write, edit, memory_write, memory_delete) and its exact declared arguments. Execution variants are derived from the tools actually installed for that run and validated server-side against their schemas. The owner can inspect that safe action in the approval card; SDK session/run references are not exposed. Group approvals remain attached to their originating chat and SDK action. A stable private notice plus the private pending-approval inbox makes the request visible to the owner. `get_approval` can inspect the owner's approval from another authorized chat, but execution and its continuation remain at the original origin. All authorized main Twin conversations already use their target owner's workspace, credentials and read/write Memory; an approval grants only its exact action. Local execution is bound to one SDK tool operation, original causal chain, target Twin and frozen configuration. Approval continuations retain the original requester/source and configuration. A fresh tool call cannot consume the approval again. Local-capable approval execution uses SDK replay=never: a crash with unknown outcome requires existing runtime reconciliation, never an automatic local replay. Platform writes retain their ProductOperation idempotency. Owner decision, budget Continue, reset, secrets and administrative actions are not tools.

Automatic `retry_reply_request` charges the **controlling** request's chain, even when rotating among old failed targets. Stable operation replay or an existing next generation cannot spend again. Exhaustion returns `held / budget_exhausted` without enqueueing. A formal exact approval may add one allowance only when that chain is full; the same transaction immediately consumes it for that retry. Cross-chat retry of an existing private task requires that exact approval before any reservation. The server labels its impact as re-executing a personal task with private execution tools. Automatic retries copy the original non-secret execution snapshot; legacy missing snapshots use version 0 with no new execution catalog. They use `tool_retry` (or retained `followup_result` semantics), so they do not become fresh human Memory experiences. Human Retry behavior is unchanged.

Followup behavior is unchanged: only an owner's private task can explicitly request the existing thirty-minute group reply followup. These tools add no polling agent, scheduler, tables, schema migration, tenant-admin authority or external notification promise. Deployment requires reloading API and Worker code after active work is idle; no production message/action is needed for validation.

Message reactions add `set_message_reaction` as a desired-state, Actor-attributed write without generating another conversation turn. See [message-reactions.md](message-reactions.md) for the API, aggregation, migration and permission boundary. New authorized group runs include request_credential, whose form and completion API remain owner-only. Saved resumable declarations retain their original collection/version and approval action variants; old frozen group runs do not gain execution capabilities.

The protocol distinguishes routine authorized reads from sensitive or mutating owner operations that need owner consent when not already granted. It supplies the current audience and requester, prohibits exposing credential values or unrelated private details, and does not treat another participant's request as owner consent. These are model conventions; local execution is not a sandbox or a malicious-command classifier. Existing per-action source restrictions, including private-origin followups and cross-chat private retries, remain unchanged.
