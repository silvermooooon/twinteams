# Implementation coordination contract — updated 2026-10-18

Current execution/transport behavior is specified in [architecture.md](architecture.md). Historical coordination ownership below does not introduce additional process roles.

Implemented integration contract. For verified behavior and remaining release gates, see `implementation-acceptance.md`.

## Boundaries
- SDK owns DatabaseSession, runtime journal and execution/recovery mechanisms; product owns identity/chat/membership/history/message/trigger/FIFO/UI projections.
- PostgreSQL is required in all environments. DATABASE_URL is explicit. Python 3.13 only.
- Development identity is explicitly labeled local. POST /auth/login accepts DEV-AAA, DEV-BBB or DEV-CCC only in explicitly opted-in local PostgreSQL development (off by default) and sets an opaque expiring HttpOnly/SameSite cookie. X-Owner-Id is rejected. Production verifies JWT subject/tenant/issuer/audience/expiration and a provisioned owner, otherwise fails closed.
- WebSocket sends commands, opaque changed revisions and bounded sender-only send acknowledgments containing correlation metadata, never chat content. HTTP reads content with authoritative permissions. Reconnect subscribes before refreshing bounded history windows. Semantic outputs remain durable SDK facts; no token tables.
- Twin-origin messages retain their actor identity and use the source owner for recipient eligibility. A model-backed `needs_response` decision gates automatic group replies, including pair groups and explicit mentions. Private direct-owner inputs retain their direct reply path. Automatic acceptances share one durable causal-chain allowance (default six); retries, recovery, child results and proactive tool sends preserve lineage. Explicit human continuation adds a recorded allowance without cancelling already accepted work.

## Proactive tools and credential configuration

`list_authorized_chats` returns all current owner-member chat metadata and identifies `owner_private_chat_id` / `is_owner_private`, from both group and private tasks. A Twin may directly report progress or request a decision in its owner's private chat. Discovery does not grant another owner's private data or bypass membership/history limits. `send_chat_message {chat_id,body,source_message_ids,reply_to_message_id?,wait_for_reply?:false}` validates the durable originating request and the owner's source/destination access, and rejects the originating chat: normal assistant output is the current chat's reply outlet. A newly composed cross-chat message is the owner's outward statement: recipients receive its prepared body without access to the originating transcript. Internal request/manifest/operation references retain audit provenance. Same-chat model output still respects its authorized audience. Stable SDK operation IDs make replay idempotent and preserve the causal chain; receipts for previously committed sends remain replayable without a second send. Never include unrelated private details in a new outward message.

Approval JSON may include the safe frozen `{tool,arguments}` action for its approver, excluding SDK internal references and secret values. The existing card's View details exposes that exact tool and arguments as escaped React text/JSON, alongside target and impact; old cards without an action remain usable. `frontend/checks/approval-details-ui.cjs` verifies all 13 action variants, legacy cards, approver filtering, escaped markup, English desktop and Chinese 390px layout without submitting any decision. Exact owner approval may authorize a single retry of an existing legitimately frozen private task with the private execution impact made explicit, without changing the retried task's frozen tool contract. `owner_ids` is capped at 100 and `source_message_ids` at 500 in platform declarations.

Platform approval action variants include `set_message_reaction`, `send_chat_message`, `create_chat`, `rename_chat`, `add_chat_members`, `create_reminder`, `update_reminder`, `create_tracking`, `update_tracking`, `delete_tracking`, `add_tracking_update`, `save_summary`, `cancel_reply_request` and `retry_reply_request`. Their arguments reuse the installed typed tool declarations. Approval cards may appear in the owner's private inbox for a group task; decision continuation stays in the originating group with frozen execution configuration and original requester/source identity. Installed non-replay-safe execution tools also offer their exact schema as approval variants; local execution remains bound to the owner, task, frozen configuration and one SDK operation. A pending card does not block later replies.

On a genuinely resumable SDK run, platform declarations are re-injected from that run's frozen tool records using only currently known platform executors. Each invocation still performs current service authorization. A saved unknown tool name cannot install an executor. Completed session history alone does not freeze a new run's declarations. New platform declarations use version `twin-teams-platform-v2`; a resumed declaration retains its saved version. Execution and delegation tools also retain the accepted declaration set on resume; new child runs use the same authorized owner assembly as main runs.

New chat membership emits an owner-targeted `personal_changed` notification with `section:'chats'` after commit. Reusing an existing direct chat does not emit a new-membership hint. The client reloads canonical bootstrap on that hint and once on connection/reconnection, preserving a still-authorized current selection, draft, detail and focus. Subscriptions compare sorted chat-ID sets, so list reordering does not reconnect. `frontend/checks/chat-discovery-ui.cjs` passes private/group scenarios for new-chat discovery, missed-hint reconnect recovery and unchanged-set reordering with fully synthetic HTTP/WS. Typecheck and production build pass; the final approval-detail build is `index-s3FTSbjB.js` / `index-BMWbdcWb.css`.

Only an explicit `wait_for_reply:true` from the owner's private Twin to an existing authorized group creates a fixed thirty-minute followup in the send transaction. A direct reply to that message or the deadline commits one terminal outcome and one `followup_result` on the original private FIFO, or a durable budget-paused delivery that the existing owner Continue API can resume. Normal model replies qualify only at completed final output; intermediate narration does not close a followup. Human messages and committed send-tool replies qualify immediately. Consumed direct replies do not also route the same owner into a group response. The existing six-reply allowance covers followup delivery on the original chain, without resetting at timeout; exhausted chains pause before invoking a model router. Waiting uses existing deadline/change hints and bounded due recovery, with no resident model/subagent. A completed empty followup final remains silent. See `twin-followups.md` for late-reply and permission-revocation behavior.

The separate local credential routes use sanitized fixed-code responses rather than the ordinary `{detail}` errors. See `local-provider-configuration.md`: only the local AAA administrator can validate a personally submitted key against the fixed official endpoint, with explicit optional local saving. Neither validation nor saving enables Runtime generation.

## Automatic chat reply entry

The composer can submit Reply for me only to the signed-in owner's Twin. Human HTTP/WS manual requests and Retry cannot invoke another owner's Twin. Automatic group replies retain needs_response/recipient routing and the shared six-reply causal budget. A known-offline recipient qualifies immediately after routing; an online recipient qualifies when ten seconds from the source message pass without their human reply or own Reply-for-me submission. Read receipts, opening the chat and leaving it do not cancel that wait. Unknown Redis presence fails closed. Continue grants budget without bypassing the original deadline or the owner-replied check; accepted tasks, approval/credential/worker/followup continuations remain valid. A recipient who goes offline during an existing online grace window is rechecked at the existing deadline, using current TTL observations rather than a new disconnect scheduler.

## Soul and Git Memory

Owner-only `/me/twin/soul` GET/PUT/DELETE edits canonical workspace SOUL.md using hash `expected_version` (null if deleted). The Twin may edit that same file through authorized owner workspace tools in any conversation; new requests freeze its current contents. Memory tools address the separate Memory store. Owner-only `/me/twin/memory/entry` PUT/DELETE uses Git SHA `expected_version` and returns 409 with `current` on conflict. Real configuration audit events supply source references. Incremental `memory_dream` requests consume visible published owner-private messages, including proactive Twin reports and continuation outputs, through a separate `message_cursor_seq`. Raw groups remain excluded. Existing FIFO/deadlines, independent SDK sessions, source/reset checks, confirmed publication and no conversation output remain; legacy queued intents retain their old request-cursor contract. The server platform prompt supplies a concise task-completion mission and has no user-facing API; reply-for-me remains scoped to writing. See `twin-git-memory.md` for migration, cancellation and uncertain-publication behavior.

The main Twin is the owner's front-facing coordinator: it handles brief communication and simple operations, delegates substantial or growing work through installed background tools, and reviews completion notifications before coordinating remaining work. Its prompt calls for staying available after dispatch and claiming delegation only after a task exists. Worker prompt assembly selects an explicit execution role, independently of summary maintenance: workers complete only the assigned subtask and return verified results to the parent, without inheriting the main coordination or parent reply-for-me writing instructions. Main and child sessions use the same owner capabilities, including Memory and delegation, while keeping separate task histories and compaction. Children can retrieve authorized history on demand. Nested results resume the immediate worker parent through the SDK durable FIFO; only its reviewed result reaches the root product FIFO. Recursive delegation uses a maximum depth of three, up to 32 distinct children per parent run, and eight active child executions per host. Spawn confirms durable queued acceptance, not startup. Workers yield while descendants run; arbitrary blocking waits can still occupy a child slot. Existing owner permissions, source checks, frozen declarations, reset fences and causal-chain limits remain.

## Uploaded files and the real workspace

Chat attachments accept every file type, with the existing four-file and 20 MiB aggregate limits. Recognized static images retain previews; other formats, including images without a supported preview, use ordinary file cards. New uploads have one physical copy in the current chat's `uploads/<id>/<original-name>`; old paths remain valid. Model input supplies metadata and absolute `workspace_path` references, never automatic image bytes. File-only messages can request a reply. Installed `read` handles text and images on demand; `bash` can process other formats. Existing paged-read and tool-result limits remain.

The private chat directory is the Twin owner's execution cwd. Group runs keep that owner cwd and receive the separate current group's shared workspace path for intended deliverables; browsing a group never lists owners' private directories. Workspace browsing lists actual directory children lazily, so generated files appear without a registration step. Hidden internal directories are omitted. Uploaded files are read-only references by convention; `uploads`/legacy `.attachments` and registered ancestors still enforce their existing attachment/node, source, draft, private-input and history permissions, including direct downloads by path ID. Unregistered group files use creation time for restricted history; where birthtime is unavailable, unknown creation time stays unavailable to history-limited members. Existing OS-level local execution remains trusted, not a new file sandbox.

Message bodies have no application character cap and remain complete in PostgreSQL. Frames exceeding the existing 64 KiB WebSocket command limit use the same HTTP send/key; this does not remove transport, memory or model context limits, nor silently truncate a message. Before deploying, run `python -m app.init_db` to widen attachment `relative_path` to `TEXT`; this repeatable additive upgrade changes no files or stored paths. See `attachment-path-schema.sql` for the reference DDL. Previously accepted SDK commands retain their immutable inputs during recovery.

## Human conversation titles

`kind=private` remains the owner's conversation with their own Twin and displays that Twin's configured name. A `kind=group` conversation with exactly two current owners displays the other owner's human Actor name to each viewer; its stored historical title is ignored and it cannot be renamed. Chat JSON includes `can_rename`, true only for group chats with at least three current owners. Bootstrap, chat detail, summary, Agent context and authorized-chat metadata use the same viewer-aware title rule.

`PATCH /chats/{chat_id} {title}` allows a current member to rename a group of at least three owners. The title is trimmed and must contain 1–256 characters (400 on invalid content, 409 for a private/two-owner chat, 403 for a nonmember). It returns the viewer's complete Chat JSON and uses the existing revision/change notification mechanism. Creating a two-owner conversation ignores a submitted title. Adding a third owner initializes a group title from all current human names; later additions preserve an existing group name. Local seed creation retains its defaults but never rewrites an existing pair/group title. No schema migration is needed; API and Worker service code both require reload to use the new display rule.

`POST /chats` with exactly one distinct other owner is a bidirectional get-or-create. A nullable unique `direct_pair_key` hashes the sorted two-owner IDs. Opposite/concurrent API calls return the same complete viewer Chat. Existing membership history policy/floor/version, settings, title and history are never reset by a reused POST; submitted title/history policy apply only when the pair is first created. The existing Chat mutation transaction rechecks current membership after a uniqueness conflict. Adding a third owner clears the key in that transaction, so a later direct chat starts a new pair rather than returning the upgraded group.

Deploy the pair-key migration before starting the new API/worker: `python -m app.migrate_direct_chats` performs only this schema/backfill, without seeding, memory work or model calls. `app.init_db` also invokes it for normal provisioning. The reference `direct-chat-schema.sql` only shows DDL; ADD COLUMN alone is insufficient because existing unique pairs must be backfilled. Ambiguous duplicate pairs cause an explicit migration failure. The generic migration never picks a canonical duplicate, deletes a conversation, merges history or alters user grants. Any individually approved empty duplicate cleanup must be separately revalidated in a maintenance transaction before backfill. There is no alias registry, new pair lock, or deterministic chat-ID reservation.

The owner-private Tracking index in chat detail, runtime context, `list_tracking`, and `GET /api/chats/{chat_id}/tracking` uses the same active-membership and source-history checks. Records retain their original chat ID, title and kind; no topic is copied. Group sources in private runtime manifests retain their `chat_context` boundary. Tracking writes, membership changes and source withdrawals emit a lightweight personal Tracking hint, so the private index can refresh without loading the conversation again. Cross-chat writes retain inherited provenance: private context is not silently made readable to other group members.
