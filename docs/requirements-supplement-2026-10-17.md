## 补充十：Runtime 负责子任务通信

来源：Sentinel_1931b07535888191a2a9065c92fd8550。原文：

> Twins 和 Sub agent 的通信属于 Agent Runtime。Twins 可以主动在任何聊天中发起消息，所以 Twins 和 Sub agent 的交互不在我们当前的讨论中，而是在 Runtime 中。
>
> 具体交互流程如下：
> 1. Sub agent 运行完成之后，会将结果通知到它的主进程（即 Twins）。
> 2. Twins 收到消息后，进行总结并发送到对应的群组或聊天中。
>
> 并且，当前 Agent Runtime 应该已经实现了相关的代码。

## 补充二十：输入模式、打断和独立审批抽屉

来源：Sentinel_d89ccca409148191b1bbaffa595dd7af。以下保留原文字样与歧义，不代改“绘画”“第 3 个”：

> “替我回复”是输入框中的一个选项。点击后，输入框周围会变色，提示当前处于该模式。该功能可以手动关闭，并且每个群组的开关状态是独立的。在 A 群组开启的这个功能，在 B 群组中不共享，需要单独再开一次  对于第二点，如果中断以后：
> 1. 已回复的需要直接撤销掉；
> 2. 如果有正在排队的，那么就开始执行排队的请求。 3. 审批：审批是各个绘画独立的，也就是说在 和自己的 twins 的私人对话中，需要有单独的审批栏。
>
> 具体设计要求如下：
> (a) 交互形式：审批栏像一个抽屉，可以从当前对话框中抽出，也可以收起来。
> (b) 累计机制：审批抽屉是可以不断累计的。例如，当前有 3 个待审批的请求，那么这个抽屉里面就要用 tab来呈现这 3 个审批。如果在这个过程中没有进行审批，又有新的审批进来了，那么需要在这个 tab里面更新到第 3 个，并且可以一直这样累计起来。 同样的设计在每个群组中是复用的。当这个群组中有事情需要当前这个人审计的时候，也会在当前的这个 chat 的输入框中弹出这个审批的抽屉 这个审批应该是一个单独的事件，它不应该阻挡每个 twins 的运行。举个例子：当 A 要求 B 的 twins 完成一件事情，但 B 的 twins 需要 B 的 owner 授权的时候，B 的 twins 应该向 B 的 owner 发起一个审批。发起之后，B 的 twins 还能够继续对话，它需要使用工具检查这个审批的状态，来了解是否能够完成这个动作。也就是说，审批不会阻止 Agent 对后续的响应

>
> 1. 会话（Chat）：
> 每一个 chat 都是一个会话。也就是说，Owner 和自己 twins 的对话、私人对话，都是单独的会话；每一个群组中每个人触发的 Agent，也是一个会话。
>
> 2. Run：
> 每一次的触发（即任何输入，可能是 Owner 的输入，也可能是其他 twins 的输入），触发 Agent 的 reaction 响应，这个过程就是一次 Run。也就是说，一个 Agent 收到一个消息，开始进行内部的 agent loop 处理，处理完成之后会有一个完整的总结，这个过程就是一次 Run。
>
> 3. Event：
> 一次 Run 会产生非常多的 Event，这就是 Event 表所需要记录的内容。
>
> 所以，我希望每一次 Run 都是一个卡片，在这个 activity 页面下面做呈现。具体规则如下：
>
> 1. Run 的定义与展示范围：
> (a) Subagent 的调用：当 Twins 触发了一个 subagent，这个 subagent 本身也是一次 Run。它会收到 Twins 的原始请求，开始内部工作，最后生成一次完整的总结并结束工作。这次调用应该作为一个单独的卡片呈现在 activity 页面中。
> (b) Twins 的响应：Twins 对一条消息的响应本身也是一次 Run，这也应该作为一个单独的卡片放在 activity 页面下面。
>
> 2. activity 页面的展示与交互：
> (a) 排序规则：需要用时间来展示这些 Run，按倒序排列，最新的放在最上面。
> (b) 状态标识：卡片图标上需要能够标识出这个 Run 是“正在进行”还是“已经完成”。
> (c) 详情展示：点击 Run 的卡片可以像抽屉一样打开详情，用链条的方式展示每一次的 Event，并能看到输入和输出。

## 补充四十一：token 可丢弃，恢复时展示完整 output

来源：Sentinel_163f756d0bc0819183270b91e8d32935。原文：

> 当前我们使用 response API，所以可以拿取到每一个 token 的数据，但是这些 token 可以认为是被放弃或者是被丢弃的。因为在每一次这种 detail 级别的 event 时，最终会有一个完整的 output 字段来整理之前的这些逐字的 token。所以当前 Agent runtime 中对这个部分的设计是逐字的，token 是可以被放弃的：1. 正常情况：只有在一切正常的时候，才可以按照 token 去渲染打字机效果。2. 恢复或重连：如果发生恢复或者是重连，那么 DB 里面只需要拿取完整的回复展示即可。3. 集群部署：在以后的集群部署中，如果跨 pod 去恢复，也可以接受这个损失，只拿取完整的 output 结果做展示即可。

结构化解释：此决定替代数据库稿此前待确认的逐 token 精确回放方案。正常连接的 token 是临时展示数据；重连与跨 pod 恢复以每个已完成语义操作/事件的已提交完整 output 为准，不只是整个 Run 的最终总结。当前操作没有完整 output 时展示运行状态，不编造缺失文本；Run、语义事件、模型/工具完整结果及 checkpoint 的持久性要求仍适用。

## 补充四十二：Twinteams 与 Agent Runtime 的职责

来源：Sentinel_8bdb5bcb16c08191869a24887683f37b。原文：

> 当前这个实现没有过多地强调 Agent 运行时的行为，因为这些都在 Agent Runtime 中重点关注并实现。所以你要明白当前 twinTeams 项目和 Agent Runtime 项目的职责

结构化解释：Twinteams 负责产品逻辑、身份/聊天/消息、业务路由与触发/FIFO、审批 UI、Tracking、工作空间及展示权限；运行循环、Session/Run/Event、工具与子任务、运行持久化/checkpoint/恢复和执行并发控制归 Agent Runtime。运行层增强留在 SDK；产品保存业务数据与 SDK 来源映射，不重复建设运行时。职责归属不等于相关能力已经全部验证实现。

## 补充四十三：本地与生产数据库选型（确认摘要）

存储更新（2026-10-18）：本地开发与部署统一使用 PostgreSQL。业务数据、权限和 FIFO 由 Twinteams 管理；执行日志、恢复、checkpoint 和租约由 Agent Runtime 管理。该选择不改变已确认的交互、来源权限、完整结果保存与项目职责。

此决定替代数据库稿此前 PostgreSQL 仅为建议、选型尚待确认的状态。业务与 Runtime 分别适配其所拥有的数据，保持相同的语义结果恢复和权限契约；本地存储选择不改变两个项目的职责。


## 补充四十四：Twins 主动消息与有条件互答（完整方案已确认）

需求来源：Sentinel_fca0adb1ac888191835278e37f931b47。以下为用户原文：

> 另外请你确认设计 当前 twins 是否有主动发消息的能力 并且 a 的 twins 给 b 发消息 这个消息 在 b 的 twins 视角需要当做和 A 的本人发消息 也就是说 两个 twins 在某些条件下可以互相对话

完整方案确认：Sentinel_5297a0cb1f3c8191b3e0795320e73836。用户原文：

> 是的 我同意 并更新设计

以下为获同意方案的结构化记录，不是逐字原文；是当前已确认设计，不再列为待确认，也不代表已实现：

- Twins 可主动向有发送授权的聊天发消息。A Twins 的消息在 B Twins 触发视角按来源 Owner A 处理，排除 A Twins 自触发；实际作者仍为 Twin，保留 Owner、消息类型、Run 与完整来源/因果链。
- 独立路由 LLM 同时判断 needs_response。感谢、确认、完成或无新信息时可以不接话，最终自动目标可为空。显式 @ 仅保证潜在目标，不在 needs_response=false 时强制回复。两位 Owner 群仍默认以对方为候选，多人群由 LLM 推测并与显式 @ 合并去重；随后逐目标遵守在线/查看/10 秒规则。
- 单条持久因果链初始默认可配置接受 6 次自动 Twin 回复，计数跨全部 Twins、聊天和 Run 共享。每个新自动接受原子预留一个名额，同一请求或重试操作去重计一次。重发、已接受请求的内部重试/恢复、subagent 结果、Run 切换、同一 Run 主动发送不能重置链或预算；真正新接受的自动 Retry 仍沿原链计一次。
- 达上限仅暂停尚未接受的新自动机会，不能停止已接受的 queued/running 请求；原 FIFO、主回复串行及接受后不因 Owner 查看而自动取消原则继续适用。
- UI 明确提示暂停并提供 Continue。真人明确 Continue 在同链增加新一段默认 6 次的自动额度，记录授权并保留原始 lineage 与累计已用量；同一授权去重，不清零历史。真实手动请求/人工 Retry 仍可用，但不隐含补充自动额度，工具不能靠标 manual 绕过上限。
- 独立新真人消息建立新链，显式 Continue 或针对原请求的人工 Retry/手动请求不重置原链。失败或取消不抹去先前接受记录。
- 另设确定性的规范化后完全相同内容防护，阻止同链不同消息的重复内容产生新的自动接话，同一首次消息的多目标与重投不因此误伤；不新增模糊/语义相似度静默丢弃。语义是否需回应交给 needs_response。防护不撤回已发消息、不停止已接受请求。
- 原始及派生内容的来源权限、私人边界持续有效。跨聊天发送必须检查目标受众及发送授权，不能自行加成员或公开私人资料。Twin 消息不能当作真人对工具副作用的批准；预算提示也不得泄露无权读取的跨聊来源。
- 因果链/预算/Continue 授权属于 Twinteams 业务层；loop、Session/Run/Event、工具/父子通信、运行持久化与恢复仍归 Agent Runtime。数据库表字段与实现还须落地，本轮只更新 Markdown 设计。
