# Owner-confirmed private Twin reset

GET `/api/me/twin/reset` returns the canonical private generation and reset status. POST requires `{idempotency_key,expected_generation}` and derives the owner exclusively from authentication. Responses contain `reset_id`, `status`, `generation`, `private_chat_id`, the original key and expected generation. A stale generation/new conflicting key returns 409 with `current`. A successful old key always returns its original receipt, even after later messages or another reset; it never clears new work. Pending receipts expose the same key and expected generation so reconnects can resume cleanup without inventing another operation. UI confirmation is required before this explicitly destructive endpoint.

The first transaction locks the existing private Chat row, advances its reset generation and persists the pending intent. It fences old private main requests, child results, approvals, credential requests, followups and Dream jobs and queues existing SDK cancellation commands. Product private message bodies and private inputs, summaries, Tracking, source manifests, Memory audit bodies and Activity projections are cleared. FK shells and execution identities remain for existing group references and internal audit. Membership's history floor advances. New private work and Memory access remain closed while cleanup is pending.

A second idempotent transaction purges only that owner's exact hashed Memory scope in retired generations, including the bare Git repository/history, legacy JSON and completed import marker. It never removes `AGENT_MEMORY_DIR`, another owner's hash or the current-generation repository. Retired generation directories and owner scopes must remain within the trusted configured root and cannot be symlinks. A failed local cleanup leaves the durable pending intent closed; the same key retries it. Missing blobs count as already cleaned. After completion, the new Memory generation starts empty and cannot reimport retired JSON. Native local Git initialization/publication and the generation switch/purge use the same existing private Chat transaction boundary. Read-only cloning and reads use checks before/after rather than a persistent DB lock. No transaction spans model or external network awaits, and no new file/distributed lock framework is added.

Private SDK session identity includes the generation. Per-model/tool/output checks reject retired requests, while exact retired private-run recognition allows cancellation and acknowledgement of old SDK child notifications without re-delivering their contents. Old Activity detail URLs and original continuation/retry/source authorization are refused. Existing private execution journals remain internal, non-reusable audit; this feature is not secure erasure of every historical SDK record or backups. It does not undo previously committed external actions or completed shell file side effects.

All group messages and group requests remain unchanged. Name, avatar, SOUL.md, Skills, credentials, prompts and the complete workspace files remain. Private WorkspaceNode records retain their owner grants and files; only links to the cleared private messages are removed. Private attachment bytes are removed only when no group message/request references them; shared group references preserve the attachment and metadata. Other owners' chats, files and Memory are untouched. Reset sends content-free owner `personal_changed` notifications for `reset` and `memory`, alongside normal scoped private changes.

Provision with `python -m app.init_db` before starting the new API/worker. It first writes legacy Soul values into canonical files (without overwriting a competing file), then drops the old DB Soul columns. The reference `twin-reset-schema.sql` adds reset columns/table but deliberately never performs a SQL-only destructive Soul drop. Stop old API/worker versions before provisioning; preflight should report counts of nonempty legacy Soul values and existing SOUL.md files without printing persona content. Reset is never executed as a deployment test on actual owner data.

Tests `test_twin_reset.py`, `test_soul_file.py`, `test_memory_dream.py` and independent `test_twin_reset_acceptance.py` use disposable PostgreSQL, temporary Git/workspaces and offline providers. They cover pending/retry, key replay after new messages, repeated reset with attachment shells, missing/shared blobs, strict owner scopes/symlinks, late draft publication, fresh runtime identity, source authorization, other-owner/group preservation, SOUL file edit/delete/migration and immediate Dream behavior.
