## 用户原文

好的 现在开始跟我一起设计整个项目的表结构 首先 在我的设计里面 每一个人都有自己的 twins 也就是说他们的身份是不一样的 twins 和 twins owner 是 1:1 的 所以在数据层面 我觉得这是需要区分出来的 另外就是对话方面 首先用户可以和自己的 twins 进行对话 其次 当你在聊天中 也就是在搜索中找到其他人的时候 这实际上是一个群组 因为这个对话框不只有你和对方 还有你的 twins 和对方的 twins 所以当前这个对话框中其实是有 4 个人在的并且我们还需要支持群组功能 也就是 group chat 这个时候 群组开启的方式和 Teams 是一样的 你可以在当前对话右上角的人数上点击“添加” 然后添加其他人的名字 当你添加其他人的时候 此时会将他和他的 twins 也加入到当前这个群中 变成一个真正的群组 这点交互逻辑和 Teams 是需要保持一致的 另外 在每个聊天的侧边栏中 我们需要有不同的行为 在和自己的 twins 的聊天界面中 这个侧边栏需要显示这个 twins 的头像 名字以及他当前的思考内容 这个思考内容用卡片的形式呈现 并且这个侧边栏需要有 table 页 点击其他的 table 时 可以看到当前这个 twins 的工作空间 它的目录结构。

在 group chat 的模式下，也就是和其他人对话，不管是你和其他人，还是你和其他更多的人，本质上都是 group chat。

所以我们当前只有两种模式：
1. 你和自己的 twins 对话
2. group chat 在 group chat 的模式下 你的侧边栏界面应该是这个 group 的共享的工作空间 然后我们还需要完成一个消息提醒 当你的 Teams 执行到某些地方 认为需要你的授权或者是需要通知你的时候 它可以发送这样的消息来通知你 你就会出现一个消息提醒 这个需要沿用现在 Teams 的消息提醒的 UI 和交互 其次 我们还有一些长期记忆功能 我们当前的 Agent Runtime 里面已经有了一些相关的基建 可以考虑复用 并且我们整个数据库的设计和 Agent 运行相关的 都要以 Agent Runtime 这个 SDK 为主 在这个 SDK 中丰富加强。所以当前其实是两个项目：
一个是 Twinteams，它负责上层的逻辑，在 Agent 运行层面需要使用 Agent Runtime 这个 SDK。我们还需要有一个 tracking 功能 这个功能的意思是当你和 你的 twins 进行对话的时候 我们会对这个 twins 的对话记录做一些总结 规划成不同的任务目标 维护这个总体的目标 并且会在这个目标上实时地更新状态。

所以在群聊的状态下，我们可能要考虑如何处理，才能让 Agent 获得足够完整的上下文，在群聊模式下也能正确处理用户的任何一次提问。因为对于群聊来说，你发的这个问题，不管是对方真人发的，还是对方的 twins 发的，它都不会第一时间触发 twins 进行回复。而是有两个标准来判断：
1. 对方是否活跃：活跃的标准是有没有登录这个平台。所以我们需要能够统计到当前用户的状态。
2. 用户有没有正在打开当前的对话框。

所以这里有三种状态：
第一种是用户直接是离线的，这种情况下Twins 发的消息在群组条件下 这个群组也是分为两种的：一个是一对一的群组 一个是多人群组 在一对一的群组中 一个人给另一个离线的人发消息 所有的消息都会立刻触发离线的人的 Twins 进行回复 但是 Twins 有自己的执行逻辑 核心思路是 Twins 不能在自己的 owner 不知情的情况下执行任何有副作用的任务 只能承担只读权限内的要求 但有一个例外 如果 owner 明确定义了某一个任务是可以默认执行的 即使这个任务是有副作用的 Twins 也可以直接执行。

下一个情况：一个用户发送一条消息，对方是在线，但是并没有查看当前的消息（即未读状态），那么此时需要留出一定时间。这个时间目前定为 10 秒钟 如果用 10 秒钟对方的 owner 还没有明确回复 那么此时会触发对方的 twins 开始对这条消息进行回复 另外最后一种是 当前对方正在查看聊天 那么此时不会自动触发 twins 回复 当前聊天中所有的消息都有两个按钮 分别是要求自己的 twins 回复和要求对方的 twins 回复 并且还有一种模式是在自己的对话框中开启的 叫做“替我回复” 此时我本人发送的消息会先发送给 twins 我可以设定替我发送的这个 twins 的提示词 然后 twins 会拿到我的消息之后替我处理 或者丰富之后再帮我回复 请你把我的这个原始的要求找个地方记录下来
