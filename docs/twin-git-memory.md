# Twin Soul, Git Memory and incremental Dream

`SOUL.md` in the Twin's existing private workspace is the sole persona source. GET/PUT/DELETE `/api/me/twin/soul` read, replace or remove that same file. PUT supplies `content` (up to 50,000 characters) and `expected_version`; DELETE supplies the hash as a query parameter. Version is SHA-256 of the file bytes, or `null` when absent. A stale version returns HTTP 409 with `current`. The first initialization preserves legacy DB Soul content or seeds the owner-adapted persona; initialization publishes only if absent, and its marker keeps deliberate deletion from being recreated. `app.init_db` performs this one-way file migration before dropping obsolete DB Soul columns; a conflicting preexisting unmarked file requires reconciliation rather than discarding either version. Name changes replace only the managed heading, prepending one if an existing file has none and retaining its body. A deleted file stays deleted on rename.

The main Twin and its authorized children use the same owner workspace in private and group conversations. They can edit SOUL.md with ordinary workspace tools, obtaining owner consent when needed and telling the owner when changing it. Main and child sessions receive the same owner read/write Memory tools in all authorized conversations. Their conversation histories and compaction remain independent; children receive explicit task materials and can read authorized history on demand. Group participants' claims are not owner instructions or verified owner facts. Existing Git CAS and private-generation guards apply across these sessions. Each new request freezes the current file content/hash; resumed requests retain their prior snapshot. Memory tools address the separate Memory store and cannot write SOUL.md through a memory key. The independent server platform prompt supplies a concise task-completion mission and has no user API. It guides targeted clarification, relevant Skills/Memory retrieval and continuation after results while keeping reply-for-me scoped to writing. Runtime protocol instructions remain separate from the editable persona.

Memory uses SDK `GitMemoryStore`. Each `(tenant,user)` has a local bare repository inside the existing hashed scope beneath `AGENT_MEMORY_DIR`. There is no GitHub service, no added lock framework and no shared checkout. First initialization publishes a prepared repository by atomic directory rename; Git ref compare-and-swap and ordinary push/rebase handle concurrent edits. Different keys merge; stale edits to the same key return a conflict. API and worker must share the same `AGENT_MEMORY_DIR` and tenant identity.

GET `/api/me/twin/memory`, `/entry?key=...` and `/search?q=...` retain their existing response shapes. PUT `/entry?key=...` requires `{content,expected_version}` (`null` only for creation). DELETE requires `key` and `expected_version` query parameters and returns `{deleted:true,key}`. Conflict responses contain `{detail:"memory_conflict",current:entry|null}`. A client must reread and explicitly merge before retrying. The entry version is the Git revision commit SHA; it is not a monotonically increasing counter. Deletion removes the entry from the current branch, while Git history remains versioned.

Every configuration edit first creates a real owner-scoped `tt_memory_edit_audit` event. Published entries reference `twin-config:<owner>` plus that audit ID. This is a host configuration ledger, not a fabricated SDK conversation. `get_memory_edit_source` validates both reference namespace and event owner before returning content. The audit records requested, published, conflict, failed or recovery-required outcomes. Git publication and PostgreSQL acknowledgement cannot be one atomic transaction: an unknown publication reports a reconciliation error and does not invent success. API errors exclude submitted bodies.

## Explicit migration

Provision the additive schema with `python -m app.init_db` (the standalone equivalent is `docs/twin-memory-schema.sql`). Then, with API/worker stopped for maintenance and the intended shared memory environment configured, run:

```sh
python -m app.migrate_git_memory --owner-id OWNER_ID
```

Omit `--owner-id` to migrate configured owners. The command does not call a model. Legacy JSON is never changed or removed; content and source references are preserved. Git import timestamps reflect the import commit rather than the old JSON write time. Imports are resumable and reject content conflicts. A completed marker prevents any future reimport, including after the owner deletes a migrated Git entry. Ordinary API/runtime access refuses unmarked legacy JSON until explicit migration; an empty new scope initializes without historical import. Do not remove the marker to undo a deletion.

## Incremental Dream

`TWINTEAMS_MEMORY_DREAM_INTERVAL_SECONDS` defaults to 14,400 seconds (minimum 60). New Dream batches read the owner's published private-chat messages: human inputs, Twin proactive reports, and visible approval/credential/worker/followup outputs. No human reply or completed originating run is required. Raw group messages stay excluded; only an actual report posted into the owner's private chat enters this scope. This changes Dream intake, not the Twin's report policy: reports are not automatically forced or copied. Group main sessions can independently write appropriate owner Memory through their existing tools.

The additive nullable `message_cursor_seq` has private Message.seq units. Legacy `cursor_seq` retains accepted-request units and is never reinterpreted. Explicit provisioning (`python -m app.init_db`, or [the standalone migration](twin-dream-message-scope.sql)) schedules existing nonempty private chats after the interval and starts new cursors at zero, allowing retained private history and previously ignored reports to be processed in bounded batches. Existing queued or recovery-required legacy intents keep their exact request/run payload and old cursor until settled; only subsequent jobs use message scope. No model starts during migration and no bodies are inspected by it. The existing Memory API keeps legacy `cursor_seq` and adds `message_cursor_seq` for clarity.

Each pass uses the existing chat/sequence index to scan at most 100 rows and selects at most 20 visible messages within a 96 KiB projection budget. Inaccessible, withdrawn and system records can be skipped without a model; only such empty pages advance the scan cursor without publication. A page containing evidence advances only after confirmed Git publication. An active mutable reply-for-me bubble forms a cursor barrier until stable; its final body is not skipped. Body/raw-input fields share a 90 KiB text budget (a single 30,000-character Chinese body fits unchanged). Fields also respect a 48,000-character cap below prompt sanitization limits. Only truly oversized fields are explicitly truncated with byte counts and a full-content hash; the original message is unchanged. Overflow messages remain for the next batch. Automatic gaps schedule the next existing deadline; explicit Dream now may return `scheduled` with no request ID after an empty scan page, scheduling a bounded continuation immediately. No resident agent or new polling loop is added.

Evidence freezes actual message ID, sequence and content hash, visible author/time/reply references and attachment names/types, with sources in `twin-chat:<chat_id>:generation:<generation>` and each real message ID as its event ID. Revalidation checks current private ownership, reset generation, visibility, provenance and exact content before each model/tool/source read. Group-derived reports are assistant claims, not automatically confirmed owner preferences. Existing Dream guidance still selects supported durable facts, rejects guesses/transient task status, resolves contradictions and avoids needless Memory rewrites. Hidden reasoning, raw tool journals, secret forms, attachment contents and unsent drafts are not loaded. Legacy in-flight jobs continue their old exact SDK user/assistant evidence contract.

Dream remains an ordinary private FIFO request with an independent `dream:<request_id>` SDK session and no conversation reply allowance consumption. It has no chat tools, Bash, credentials, children or output projection. Existing Memory and manual edit evidence remain available for consolidation; owner corrections/deletions retain priority.

Source access is rechecked before model calls and source reads. Manual configuration edits from the earliest selected experience onward are supplied as real audit evidence; their keys cannot be rewritten/deleted by that batch's older experiences. A queued draft is invalidated if these edits change. New experiences accepted after a manual deletion may later support learning again; this is an incremental cutoff, not a permanent global tombstone. Manual audit batches are bounded to 100; an oversized owner batch records a deferred failure without blocking another owner's scheduling.

Only confirmed Git publication advances `cursor_seq`. Known failure, conflict or cancellation retains the old cursor and schedules a fresh attempt after the interval, with a new session/draft. A publication whose result is unknown preserves `recovery_required` and has no automatic next deadline. Its business request terminates and releases the private lane so ordinary owner work continues. Recovery checks the exact `Memory-Operation` trailer in Git; an operator/runtime may confirm an actual publication through `confirm_memory_dream_publication`, without replaying the draft. Read errors and absent receipts never become inferred success. Generic user Retry is disabled for Dream jobs. The owner can request an immediate fresh known-outcome attempt using POST `/api/me/twin/memory/dream`. It returns `queued`, `already_queued`, or `nothing_to_process`, with an optional request ID. The same owner state and private FIFO deduplicate a queued/running attempt. Unknown publication still blocks another attempt. Current unprocessed experiences are included immediately; without new experiences, existing Memory can be consolidated using a real owner configuration audit event and its actual entry source references. An empty Memory with no new experiences starts no model and creates no invented facts. An unfinished human request is kept below the initial manual cursor so its eventual completion is never skipped. Cancellation after an acknowledged push still records the confirmed cursor while keeping the request cancelled.

GET `/api/me/twin/memory/status` returns Git enabled/mode and read-only Dream status, next ISO deadline, cursor, last publication version/success time and diagnostic. It does not reveal filesystem paths. Cursor/state are durable PostgreSQL rows, so restart keeps the original deadline and queued job. API, worker and migration require the additive tables and columns before startup.

## Validation

`tests/test_git_memory.py` uses temporary bare repositories for explicit source-preserving migration, deletion/no-reimport, concurrent initialization, independent-file publication, same-key conflict and real HTTP owner-only CAS/audit APIs. `tests/test_memory_dream.py` uses isolated PostgreSQL for fixed future due times, incremental selection including human retry after 55 ineligible retries, cancellation, failure, unknown publication/lane release, per-owner scheduling isolation, manual edit invalidation and the complete process→SDK→Git→cursor chain. `tests/test_dream_runtime.py` covers runtime recovery/cancellation, bounded model calls, exact evidence, source authorization and protected manual edits using fake providers. No test reads real owner memory or calls a model service.

Owner-confirmed reset clears private conversation projections and all retired-generation Git/legacy Memory data. It preserves the complete workspace, SOUL.md, Skills, credentials and identity settings. See [Private Twin reset](twin-reset.md).
