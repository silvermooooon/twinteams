# Current architecture — 2026-10-27

## Processes and state

Run API replicas separately from one active `python -m app.worker` execution service. Single-active scheduling is a deployment convention, not another Redis or PostgreSQL lock. API startup validates provisioned schemas and never starts Agents, recovery, or a scheduler. The worker owns model execution, routing admission, notification delivery and centralized compensation.

PostgreSQL owns business facts, accepted commands, semantic journals, run projections, permissions and execution leases. `tt_reply_requests`/`tt_dispatch_outbox` record business acceptance and its SDK handoff; an acknowledgment means **business_persisted**, not execution or completion. Worker delivery calls SDK idempotent acceptance using the same request ID. A crash between the two ORM transactions in the same PG database is recovered by repeating that handoff. `ReplyLane` retains acceptance sequence and historical mappings; it does not serialize independent chat tasks or claim an executor. Only SDK session lease/fence grants execution, including child sessions. Two ExecutionHosts independently batch lease renewal and control checks for foreground and background work. Foreground admission defaults to 8 root tasks per worker and 2 per owner on that worker; background admission independently defaults to 2 roots and 1 per owner. Routing retains 2 reserved foreground-host root slots. Foreground children have 8 execution slots; background children independently have 2. Each parent run retains the existing limit of 32 distinct children and maximum nesting depth of three.

These are per-worker admission limits, not a cross-worker global quota. `TWINTEAMS_MAX_RUNNING`/`TWINTEAMS_MAX_PER_OWNER` control foreground work; `TWINTEAMS_MAX_BACKGROUND_RUNNING`/`TWINTEAMS_MAX_BACKGROUND_PER_OWNER`/`TWINTEAMS_MAX_BACKGROUND_CHILDREN` control background work. A foreground limit of one does not reduce background capacity. Classification uses persisted `ReplyRequest.background` (including peer Duet auto work), inherited by continuations and child execution; it is independent of owner-facing Activity visibility. Summary preparation, Dream, owner-answer continuations and recovered children retain the original execution pool. CPU, database and provider capacity remain physically shared. Both pools preserve the same session FIFO, leases, cancellation and recovery boundaries.

Each independent incoming message, system review, saved-task occurrence and Dream uses its own SDK session. Chat history is authorized shared context; a session is one task journal. Explicit `continuation_of_request_id` binds questions, credentials, exact approvals, child results and followups to their originating task session. Only turns within that session wait for one another, and SDK leases remain authoritative. Already accepted commands and old session identities are retained unchanged for recovery. Cancellation targets one request; unrelated tasks continue. Active task and worker metadata helps new requests avoid duplicating existing work; it grants no extra authority. Owner workspace and Git Memory remain shared, with existing version checks, Git publication CAS and reset guards. Conversation checkpoint work remains content-addressed, leased and validated before save.

Runtime identity belongs to the executing Duet's owner. Human conversations (`kind=group`, pair or multi-person) accept only human participation. An owner addresses their own Duet in `kind=private`; separate `kind=duet` threads coordinate consenting owners' Duets. Each thread inherits its initiating task's causal chain. All owners must approve once or hold every required directed peer grant before the opening is published and routing starts. Always consent creates owner-to-peer grants; revocation closes dependent threads and cancels pending work. Owners inspect Duet threads read-only and retain approval, close and Continue controls. Owner-authorized create/rename/member tools continue to manage human chats through existing owner membership checks; peer-origin requests require exact owner action approval. These metadata operations publish no message and start no automatic response, and cannot add participants to fixed Duet threads. Connection consent grants communication only, never arbitrary action authority.

Private and approved Duet runs use their own owner's Soul, Skills, workspace, credentials and read/write Memory. No peer private Memory is loaded. Main and child sessions have the same capabilities and independent task histories/compaction; children return results to their immediate parent. Owner-only credential forms provide bindings, not action consent. Exact action approvals preserve owner, task, configuration and operation. Local execution shares OS privileges and is not a sandbox. Source provenance, audience restrictions and private reset guards remain separate from connection permission. Duet-origin Tracking stays within that thread; private Tracking aggregates own and authorized human-group/Duet topics with their original chat IDs.

Redis stores presence TTLs and carries disposable Pub/Sub hints. It has no task state machine, command authority, execution locks or token history. PG changes and their change-outbox row commit together. Post-commit notification is a fast path; the relay retries unpublished rows in batches of 100. A published row means delivery was attempted, never that browsers received it. Duplicate or lost hints are allowed.

## Scheduling and recovery

Normal work hints include a chat/session scope. Only that scope's indexed candidates, approvals, pending child results, task-session heads and deadlines are read. Output/activity-only changes do not trigger a global task sweep. Worker status and already-relayed notifications do not feed back into task scheduling. Earliest known due times arm an in-memory timer. Owner admission is applied before candidate limits so one owner's old queues cannot hide another owner's work.

Every 60 seconds one worker compensates with bounded index reads, including SDK expired/unowned command candidates and accepted child-result notifications. It does not scan all lanes, sessions, event histories or spawn a recovery worker in an API process. Candidate cursors bound recovery/notification pages. Unknown tool outcomes remain paused for explicit reconciliation. SDK child terminal commit also accepts the parent notification atomically; product acceptance precedes SDK notification acknowledgment. Normal session hints read notifications for that parent session; global pending notification reads occur only during centralized compensation.

## Browser transport and permissions

`/api/ws` protocol version 1 carries send/reply/stop/presence commands and opaque scope invalidations. Commands include a stable `command_id`; retries reuse that ID. `ack.accepted=business_persisted` is returned after business transaction commit. Presence uses `presence_renewed` because a TTL-only renewal is intentionally ephemeral. The browser retains pending commands across reconnects and resends their original IDs.

Chat-change broadcasts contain only `{v:1,type:"changed",chat_id,revision}` for authorized subscriptions. No model text, request IDs, private-input metadata or tool output is broadcast. User-visible content is fetched through HTTP with current membership, history-floor and provenance checks. There is no permission cache authorizing sensitive streamed content. JWT/cookie expiry closes sockets; consequential commands authenticate independently. Origin is checked, queues are bounded to 64 frames and deployment WebSocket limits are 64 KiB. Slow consumers reconnect and reload. Owner-targeted `personal_changed` hints contain a section name, not content. New memberships emit `section:"chats"` after commit; clients reload canonical bootstrap on that hint and on connection/reconnection, then subscribe using a stable sorted chat-ID set.

The sending socket additionally receives an `ack.result` for its own committed send: `message` contains only ID, chat ID, sequence, creation time, state and sender correlation key; `request` contains only ID, chat ID, status, source, source-message ID, acceptance time and requester correlation key. Either is null when absent. This uses the existing send result without another chat read, and carries no body, raw input, attachment data or runtime diagnostics. It confirms the authenticated caller's operation rather than granting content access; socket expiry still applies and canonical HTTP content remains subject to current permissions. HTTP message/request projections expose `client_request_key` only to the sending/requesting owner, including the owning request key on a retained historical reply-for-me record. The existing key also reconciles a local message when a canonical HTTP read arrives before its ACK. “Sent” means server-persisted, not delivered, read or model-completed. New Reply for me submissions and attempts to enable that retired mode are rejected. Its retained fields and historical records exist only for compatibility and audit; they cannot re-enable agent publication in human chats.

The client subscribes before its synchronization reload. It keeps no token replay cursor. Each API process centrally compares the unique active scopes' revisions every 60 seconds to compensate for lost changes, then rechecks each changed subscription's authority. Authentication expiration uses a local deadline rather than per-token/per-pong database queries. A transport hint is never proof of permission.

HTTP chat snapshots contain the latest 100 messages by default (maximum page size 200), `revision`, `has_more`, and `before_seq`. This is **bounded-window refresh on change**, not a durable incremental event API. Earlier history uses keyset pages. Loaded pages are reauthorized and replaced on change so withdrawals and changed grants do not survive as stale merged content; scroll position is anchored. Unread counts preserve exact product semantics: direct messages use indexed aggregates; dependent messages require authorization-metadata checks without reading historical bodies. This count still has a cost proportional to unread dependent metadata.

Activity lists read `tt_activity_runs` with keyset pagination; details read a bounded run/sequence page from the SDK journal. Owner-facing lists and details include only the projection's `user_visible` runs: scheduled tasks, system reviews, memory reviews and their continuations/children are hidden; user-conversation work and ordinary Duet collaboration remain visible. The flag is fixed on projection creation from the triggering request context; it does not restrict internal activity, task coordination, execution journals or owner messages. A partial index filters before pagination. The additive activity-visibility upgrade classifies existing projections once in the same transaction that adds the field; subsequent startup checks never traverse historical ancestry. Parent/child identity and summary/status are projected on writes. Older Activity is imported only by explicit `app.init_db --backfill-activity`, using indexed business/run projections rather than replaying journals at API startup.

## Presence and I/O

Redis TTL renewal does not write PostgreSQL. Presence, focus and read receipts describe human attention but never trigger Duet participation. The old offline/unread ten-second group-reply path is retired. Approved Duet messages route immediately when a concrete response is needed, subject to current consent, source access, exact duplicate checks and the original chain's shared six-reply budget. Courtesy and closure loops stay silent. Only explicit human Continue adds allowance; an approval, retry, child result, timeout or new thread cannot reset spending. Human-group projections and reconstructed context hide historical agent messages; checkpoints depending on those messages cannot be reused. Notification hints contain no message bodies and notification metadata uses the same current authorization.

Synchronous SQLAlchemy transactions execute as whole jobs in an eight-thread database pool with at most 64 admitted jobs per process. Runtime/network awaits stay on the event loop; no transaction is held over an await. PostgreSQL row/unique constraints replace the old process-wide RLock. Workspace files and private runtime memory still require persistent shared storage before deploying workers on different machines.

Message-page projection batches receipts, actors, request metadata and attachments. Recursive source checks reuse metadata and decisions only within the current read, with fresh membership/source checks in each new transaction; no cross-request content or authorization cache is introduced. Bootstrap still checks dependent unread history, and runtime context still preserves authorized full history, so their cost can grow with retained history.

Disposable text, thinking and tool-argument stream deltas do not perform product database checks or generate UI content. They still honor the local abort signal. Durable request, tool and output boundaries retain generation/authorization checks; existing stop/reset delivery aborts the SDK independently of token arrival. Running status is published only after the actual SDK run starts.

## Provision and launch

`python -m app.init_db` is an explicit repeatable upgrade. It applies additive business changes and SDK packaged migrations through `upgrade_schema`; normal API/worker startup checks structure only. `--backfill-activity` is an explicit optional historical projection import. Both roles require database URLs and `TWINTEAMS_REDIS_URL`. Only the worker needs model credentials. See the README for local commands and `checks/local_stack.py` for managed local process logs/PIDs.
