# Current architecture — 2026-10-29

## Processes and state

Run API replicas separately from one active `python -m app.worker` execution service. Single-active scheduling is a deployment convention, not another Redis or PostgreSQL lock. API startup validates provisioned schemas and never starts Agents, recovery, or a scheduler. The worker owns model execution, durable peer-message delivery, notification delivery and centralized compensation.

PostgreSQL owns business facts, accepted commands, semantic journals, run projections, permissions and execution leases. `tt_reply_requests`/`tt_dispatch_outbox` record business acceptance and its SDK handoff; an acknowledgment means **business_persisted**, not execution or completion. Worker delivery calls SDK idempotent acceptance using the same request ID. A crash between the two ORM transactions in the same PG database is recovered by repeating that handoff. `ReplyLane` retains acceptance sequence and historical mappings; it does not serialize independent chat tasks or claim an executor. Only SDK session lease/fence grants execution, including child sessions. Two ExecutionHosts independently batch lease renewal and control checks for foreground and background work. Foreground admission defaults to 8 root tasks per worker and 2 per owner on that worker; background admission independently defaults to 2 roots and 1 per owner. Foreground children have 8 execution slots; background children independently have 2. Each parent run retains the existing limit of 32 distinct children and maximum nesting depth of three.

These are per-worker admission limits, not a cross-worker global quota. `TWINTEAMS_MAX_RUNNING`/`TWINTEAMS_MAX_PER_OWNER` control foreground work; `TWINTEAMS_MAX_BACKGROUND_RUNNING`/`TWINTEAMS_MAX_BACKGROUND_PER_OWNER`/`TWINTEAMS_MAX_BACKGROUND_CHILDREN` control background work. A foreground limit of one does not reduce background capacity. Classification uses persisted `ReplyRequest.background` (including peer Duet auto work), inherited by continuations and child execution; it is independent of owner-facing Activity visibility. Summary preparation, Dream, owner-answer continuations and recovered children retain the original execution pool. CPU, database and provider capacity remain physically shared. Both pools preserve the same session FIFO, leases, cancellation and recovery boundaries.

Each independent incoming message, system review, saved-task occurrence and Dream uses its own SDK session. Chat history is authorized shared context; a session is one task journal. Explicit `continuation_of_request_id` binds questions, credentials, exact approvals and child results to their originating task session. Only turns within that session wait for one another, and SDK leases remain authoritative. Already accepted commands and old session identities are retained unchanged for recovery. Cancellation targets one request; unrelated tasks continue. Active task and worker metadata helps new requests avoid duplicating existing work; it grants no extra authority. Owner workspace and Git Memory remain shared, with existing version checks, Git publication CAS and reset guards. Conversation checkpoint work remains content-addressed, leased and validated before save.

Active Agents and SDK child drivers own their subagent managers. The bridge keeps only weak lookup references, so completed task histories can be collected; a later continuation reconstructs missing managers from the existing durable state. Pure progress events check local cancellation without rereading product provenance. Model calls, tool calls and committed outputs retain their authorization boundaries.

Runtime identity belongs to the executing Duet's owner. Human conversations (`kind=group`, pair or multi-person) accept only human participation. An owner addresses their own Duet in `kind=private`; separate `kind=duet` threads coordinate consenting owners' Duets. Each thread inherits its initiating task's causal chain. All owners must approve once or hold every required directed peer grant before the opening is published and peer delivery starts. Always consent creates owner-to-peer grants; revocation closes dependent threads and cancels pending work. Owners inspect Duet threads read-only and retain approval, close and Continue controls. Owner-authorized create/rename/member tools continue to manage human chats through existing owner membership checks; peer-origin requests require exact owner action approval. These metadata operations publish no message and start no automatic response, and cannot add participants to fixed Duet threads. Connection consent grants communication only, never arbitrary action authority.

Private and approved Duet runs use their own owner's Soul, Skills, workspace, credentials and read/write Memory. No peer private Memory is loaded. Main and child sessions have the same capabilities and independent task histories/compaction; children return results to their immediate parent. Owner-only credential forms provide bindings, not action consent. Exact action approvals preserve owner, task, configuration and operation. Local execution shares OS privileges and is not a sandbox. Source provenance, audience restrictions and private reset guards remain separate from connection permission. Duet-origin Tracking stays within that thread; private Tracking aggregates own and authorized human-group/Duet topics with their original chat IDs.

Redis stores presence TTLs and carries disposable Pub/Sub hints. It has no task state machine, command authority, execution locks or token history. PG changes and their change-outbox row commit together. Post-commit notification is a fast path; the relay retries unpublished rows in batches of 100. A published row means delivery was attempted, never that browsers received it. Duplicate or lost hints are allowed.

## Peer-message delivery

Every published message in an active approved Duet channel is durably delivered to every other participating Duet. There is no relevance classifier or needs-response gate. Receipt is not a requirement to answer: a Duet may finish silently when no useful response or owner report is needed. An ordinary terminal assistant final publishes one peer message in its current Duet channel; intermediate tool-loop text stays in the journal. `send_chat_message` explicitly sends to another approved channel or the owner’s private chat. A private report can be followed by an empty final without posting a courtesy reply to peers.

The original causal chain permits six published peer messages across its channels, including the opening. The sixth message is delivered; a seventh prepared message waits unsent. Receiving a message, private owner reports, owner questions and answers, task execution, child results and retries do not themselves spend peer-message allowance. An active participant can explicitly Continue a waiting exchange to add six sends to the same chain. Prepared messages publish only after that authorization and current permission checks. Stable send identities and consent keys prevent double publication or duplicate grants.

Published messages are independent delivered snapshots in private, human and approved Duet conversations. Readers and new runtime contexts check the current chat membership, the message's own history position and publication state; human chats still exclude agent records. Later changes to an audit ancestor do not retract a delivered answer. A message's own withdrawal or a history/reset boundary still removes that message. Source IDs, ContextManifest and complete SDK journals remain audit evidence, not a recursive reading permission graph. Quotes, owner-selected message references and original file downloads independently enforce the original record's current access; unavailable originals become placeholders without hiding the delivered text. A runtime manifest freezes the exact snapshots and visible originals read in that run, including their content hashes and origin grants. Execution and publication revalidate those direct inputs, current destination permission, reset state and consent. Unsent pending statements receive no snapshot exemption and consume neither sequence nor allowance when authorization fails.

## Scheduling and recovery

Normal work hints include a chat/session scope. Only that scope's indexed candidates, approvals, pending child results, task-session heads and deadlines are read. Output/activity-only changes do not trigger a global task sweep. Worker status and already-relayed notifications do not feed back into task scheduling. Earliest known due times arm an in-memory timer. Owner admission is applied before candidate limits so one owner's old queues cannot hide another owner's work.

Every 60 seconds one worker compensates with bounded index reads, including SDK expired/unowned command candidates and accepted child-result notifications. It does not scan all lanes, sessions, event histories or spawn a recovery worker in an API process. Candidate cursors bound recovery/notification pages. Unknown tool outcomes remain paused for explicit reconciliation. SDK child terminal commit also accepts the parent notification atomically; product acceptance precedes SDK notification acknowledgment. Normal session hints read notifications for that parent session; global pending notification reads occur only during centralized compensation.

## Browser transport and permissions

`/api/ws` protocol version 1 carries send/reply/stop/presence commands and opaque scope invalidations. Commands include a stable `command_id`; retries reuse that ID. `ack.accepted=business_persisted` is returned after business transaction commit. Presence uses `presence_renewed` because a TTL-only renewal is intentionally ephemeral. The browser retains pending business commands across reconnects and resends their original IDs. Presence bypasses that queue: disconnected heartbeats are discarded and reconnection sends the current state.

Chat-change broadcasts contain only `{v:1,type:"changed",chat_id,revision}` for authorized subscriptions. No model text, request IDs, private-input metadata or tool output is broadcast. User-visible content is fetched through HTTP with current membership, message history-floor and publication-state checks. There is no permission cache authorizing sensitive streamed content. JWT/cookie expiry closes sockets; consequential commands authenticate independently. Origin is checked, queues are bounded to 64 frames and deployment WebSocket limits are 64 KiB. Slow consumers reconnect and reload. Owner-targeted `personal_changed` hints contain a section name, not content. New memberships emit `section:"chats"` after commit; clients reload canonical bootstrap on that hint and on reconnection. The first socket connection shares the initial bootstrap load instead of repeating it. Subscriptions use a stable sorted chat-ID set.

The sending socket additionally receives an `ack.result` for its own committed send: `message` contains only ID, chat ID, sequence, creation time, state and sender correlation key; `request` contains only ID, chat ID, status, source, source-message ID, acceptance time and requester correlation key. Either is null when absent. This uses the existing send result without another chat read, and carries no body, raw input, attachment data or runtime diagnostics. It confirms the authenticated caller's operation rather than granting content access; socket expiry still applies and canonical HTTP content remains subject to current permissions. HTTP message/request projections expose `client_request_key` only to the sending/requesting owner, including the owning request key on a retained historical reply-for-me record. The existing key also reconciles a local message when a canonical HTTP read arrives before its ACK. “Sent” means server-persisted, not delivered, read or model-completed. New Reply for me submissions and attempts to enable that retired mode are rejected. Its retained fields and historical records exist only for compatibility and audit; they cannot re-enable agent publication in human chats.

The client subscribes before its synchronization reload. It keeps no token replay cursor. Each API process centrally compares the unique active scopes' revisions every 60 seconds to compensate for lost changes, then rechecks each changed subscription's authority. Authentication expiration uses a local deadline rather than per-token/per-pong database queries. A transport hint is never proof of permission.

HTTP chat snapshots contain the latest 100 messages by default (maximum page size 200), `revision`, `has_more`, and `before_seq`. This is **bounded-window refresh on change**, not a durable incremental event API. A cold chat opens on the latest 30 messages and requests earlier history in keyset pages of 100. The same login retains up to five visited windows of at most 130 messages, including their scroll position. Switching back displays a valid cached window before its authorized background refresh; larger windows retain only the latest 30 and reopen at the bottom. Newer revisions invalidate their chat cache. Authentication/account changes, reset, access loss and disconnection clear incompatible state; existing personal `tracking`/`chats` hints invalidate private windows because those hints also cover withdrawn sources and membership changes. An invalidation generation prevents older private responses from repopulating the cache. While the chat stays open, explicitly loaded earlier pages are reauthorized and replaced on change so withdrawals and changed grants do not survive as stale merged content; scroll position is anchored. Unread counts use a grouped database aggregate over currently published messages within membership history floors. Sidebar previews use one indexed latest-row lookup per chat inside one SQL request and return at most 300 characters; neither operation loads or hashes audit ancestors.

Activity lists read `tt_activity_runs` with keyset pagination; details read a bounded run/sequence page from the SDK journal. Owner-facing lists and details include only the projection's `user_visible` runs: scheduled tasks, system reviews, memory reviews and their continuations/children are hidden; user-conversation work and ordinary Duet collaboration remain visible. The flag is fixed on projection creation from the triggering request context; it does not restrict internal activity, task coordination, execution journals or owner messages. A partial index filters before pagination. The additive activity-visibility upgrade classifies existing projections once in the same transaction that adds the field; subsequent startup checks never traverse historical ancestry. Parent/child identity and summary/status are projected on writes. Older Activity is imported only by explicit `app.init_db --backfill-activity`, using indexed business/run projections rather than replaying journals at API startup.

## Presence and I/O

Redis TTL renewal does not write PostgreSQL. Presence, focus and read receipts describe human attention and do not trigger Duet participation. Published approved-channel messages are delivered directly, subject to consent and source access. The receiver may remain silent. Human-group projections and reconstructed context hide historical agent messages; checkpoints depending on those messages cannot be reused. Notification hints contain no message bodies and metadata uses current authorization.

Synchronous SQLAlchemy transactions execute as whole jobs in an eight-thread database pool with at most 64 admitted jobs per process. Runtime/network awaits stay on the event loop; no transaction is held over an await. PostgreSQL row/unique constraints replace the old process-wide RLock. Workspace files and private runtime memory still require persistent shared storage before deploying workers on different machines.

Message pages fetch only display fields, with receipts, actors, request metadata and attachments loaded in fixed batches. Human reference commands additionally load the metadata needed for their original-source card. Historical question cards retain their text; a batch of current origin-request, source-message and membership metadata disables actions after withdrawal, access loss, cancellation or reset. Actual answers still validate the original run's direct inputs. Bootstrap loads profiles only for owners connected to the viewer’s chats, including former participants needed for historical names. Tracking is a separate sidebar read. Bootstrap and chat GETs never create settings, provision schedules or take write locks: owner creation provisions the four-hour system review, and missing chat settings use presentation defaults until PATCH persists a choice. Read receipts validate and insert one batch. Direct runtime input checks share only transaction-local metadata; no persistent content or permission cache is added. Approval inboxes and shared-file projections batch their related records rather than querying per item.

The demo retains complete people-search results, joined-chat lists, reminders, Tracking indexes/updates and shared-file lists; these endpoints currently have no pagination contract. The acceptance workload is 5,000 messages, 100 chats, 100 pending questions/approvals, 100 shared files, 100 Memory entries and ten concurrent clients. Three-second successful-response checks apply to that measured envelope, not an unlimited database or unlimited transfer size. A larger deployment must add explicit list cursors with matching UI before increasing this envelope; results are never silently truncated to pass a timing test.

Disposable text, thinking and tool-argument stream deltas do not perform product database checks or generate UI content. They still honor the local abort signal. Durable request, tool and output boundaries retain generation/authorization checks; existing stop/reset delivery aborts the SDK independently of token arrival. Running status is published only after the actual SDK run starts.

## Provision and launch

The message-channel upgrade is explicitly breaking, not additive. Before applying it to an existing database, confirm old execution is idle, stop the old worker and APIs gracefully, then run `python -m app.init_db` explicitly. Normal API/worker startup only validates the schema and never runs this cleanup. The versioned product DDL is [006_duet_message_channels.sql](../backend/app/sql/006_duet_message_channels.sql). It removes `tt_automatic_reservations`, `tt_trigger_candidates`, `tt_routing_decisions`, `tt_twin_followups` and the old request reservation column; clears the old allowance grants and resets peer-send counters to six; reconciles the specified old communication request/outbox and budget-paused child metadata; and provisions pending messages. It does not delete messages, owner communication consent, credentials, workspace files or SDK journals. SDK session recovery and its independent legacy mappings are unaffected.

Provisioning also applies canonical SDK packaged migrations through `upgrade_schema`. `--backfill-activity` remains an explicit optional historical projection import. Both roles require database URLs and `TWINTEAMS_REDIS_URL`; only the worker needs model credentials. See the README for local commands and `checks/local_stack.py` for managed local process logs/PIDs.
